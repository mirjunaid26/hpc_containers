Containerizing HPC Workflows

From namespaces and single-file SIF images to Slurm jobs, GPUs, MPI and an LLM fine-tuning job on a real supercomputer.

Junaid Mir · AI and HPC Advisor, ZIM, University of Duisburg-Essen & HPC.NRW

On 22 September 2026 I ran a three-hour, hands-on workshop on containers for HPC at SciCoCo.nrw in RWTH Aachen. Participants included master's and PhD students, HPC administrators and consultants from NRW universities and the Jülich Supercomputing Centre, all looking for software that runs the same way on a laptop and on an HPC cluster.

This post is the long-form version of that workshop. It starts broad and adds detail as it goes, so you can form a correct mental model of the whole workflow before we get to the parts that fail in practice. Every command here was run on JURECA (Pre-Exascale Modular Supercomputer operated by Jülich Supercomputing Centre at Forschungszentrum Jülich) while preparing the session, and every exercise file is in the workshop repository.

The post follows the two 90-minute sessions of the workshop:

  1. Why containers and what a container really is: kernels, namespaces, and the SIF image format.
  2. Interacting with and building images: definition files, fakeroot, sandboxes, tests, signing.
  3. Running on the cluster: batch scripts, bind paths, and filesystems.
  4. GPUs and NVIDIA NGC, then MPI and I/O.
  5. A capstone LLM job, and everything that broke on the way.
Notes
  • Commands target Apptainer 1.x. SingularityCE accepts almost all of them with singularity in place of apptainer.

1Why containers on HPC

Scientific software has deep dependency trees: compilers, MPI, CUDA, math libraries, and a Python or R stack on top. The versions on your workstation, on the test cluster and on the production system drift apart, and "it works on my machine" becomes a week of rebuilding. Journals and funders increasingly ask for pipelines others can rerun, which turns this into a requirement.

A container packages your application together with its root filesystem and environment, so the whole stack moves as one unit. Unlike a virtual machine, it does not bring its own kernel. It runs as an ordinary process on the host kernel, which is why it starts in milliseconds and runs at near-native speed.

Why not just Docker?

Docker made Linux containers usable for everyone, but its classic design runs a root-owned daemon, dockerd. Anyone who can talk to that daemon effectively has root on the host, which no shared cluster can accept. Rootless Docker exists but is not yet a complete replacement, and Docker was never designed around multi-user batch schedulers.

That gap is why Singularity was created for scientific computing. In 2021 the project split: Apptainer joined the Linux Foundation, and SingularityCE continues under Sylabs. Both are actively developed, and the command line and image format remain nearly identical. Apptainer is now the default container runtime at most HPC centres, including many in Germany.

It is not the only option. Podman (with podman-hpc), Charliecloud, Sarus, Shifter and Enroot/Pyxis all run on production systems. The real dividing line is between a root daemon and daemonless, rootless runtimes, and Apptainer is one answer to that problem.

2What a container really is

A container is a regular Linux process with a restricted view of the system. Two kernel features do the work:

  • Namespaces limit what a process can see: its own mount table, process IDs, hostname, users, and so on.
  • Cgroups limit what a process can use: CPU, memory, I/O.

There is no hypervisor and no second kernel. That is why containers are fast, and also why portability has a limit: an image built for x86 will not run on an ARM node, because the CPU and kernel still belong to the host.

Images and containers

An image is a static filesystem snapshot, the blueprint. A container is a running instance of it. Docker stores images as a stack of layers managed by its daemon. Apptainer stores an image as a single file in the Singularity Image Format (SIF): a compressed, read-only SquashFS filesystem plus metadata, an optional embedded definition file and optional cryptographic signatures.

A single file matters more on HPC than it first appears. You can scp it between clusters without a registry, keep it next to your data on a parallel filesystem, and checksum it like any other artifact.

DockerApptainer
DaemonYes, root-ownedNone
Runs asroot by defaultyour own user (same UID/GID inside and out)
Image formatOCI layerssingle SIF file
Isolation defaultstrong, separate network and filesystemminimal: home, GPUs and interconnect stay reachable
Typical homecloud, CI, microservicesHPC batch jobs

The last row is the design philosophy in one line. Apptainer prefers integration over isolation: inside the container you are still yourself, your home directory is there, and the GPUs and high-speed network are usable. That is exactly what an HPC job needs and exactly what a web service usually does not.

3Pull, shell, exec, run

Before your first pull

Apptainer caches image layers in ~/.apptainer and builds in /tmp. On many clusters home quotas are small (5 GB on our training project), and a single PyTorch image fills that. Point both at project or scratch storage first:

export WORK=$PROJECT_training2638/container-workshop/$USER
mkdir -p $WORK/apptainer_cache $WORK/apptainer_tmp
export APPTAINER_CACHEDIR=$WORK/apptainer_cache
export APPTAINER_TMPDIR=$WORK/apptainer_tmp   # must exist before you build

Add the export lines to ~/.bashrc, or they are gone in your next terminal.

Getting an image

apptainer pull docker://ubuntu:22.04          # → ubuntu_22.04.sif

Apptainer downloads the OCI layers from Docker Hub and converts them into a single SIF. This works for almost any public Docker image, which means the entire Docker ecosystem is available to you without Docker.

Three verbs

apptainer shell ubuntu_22.04.sif                     # interactive prompt inside
apptainer exec  ubuntu_22.04.sif cat /etc/os-release # one command, then back
apptainer run   ubuntu_22.04.sif                     # the image's %runscript

A quick test that reveals the security model: apptainer exec ubuntu_22.04.sif whoami prints your username, not root. The image's filesystem is read-only by default, so you can't change files inside it unless you use a writable sandbox or --fakeroot during a build.

Bind mounts

Your data should stay on the cluster's filesystems, not inside the image. A bind mount maps a host directory into the container. Apptainer binds $HOME, /tmp and the current directory by default (sites can configure more), and you add others with --bind host:container.

Gotcha

If the destination path doesn't exist inside the container, Apptainer creates the mount point silently. A typo in the container path doesn't fail; your program just looks in the wrong place.

4Building your own images

Pulling covers a lot, but sooner or later you need your own stack. In Apptainer, a definition file is the recipe and the SIF is the reproducible artifact. Here is the first one participants built:

exercises/01_hello.defExercise 2
Bootstrap: docker
From: ubuntu:22.04

%post
    apt-get update && apt-get install -y bash

%environment
    export GREETING="Hello from Apptainer!"

%runscript
    echo $GREETING
    exec "$@"

%labels
    Author  Student
    Version v1.0
  • Bootstrap/From: where the base image comes from (docker, library, localimage, debootstrap …).
  • %post: runs once at build time; installs and compiles go here.
  • %environment: set every time the container runs.
  • %runscript: what apptainer run does.
  • %labels: metadata you can read back later with inspect.

Further sections exist for more complex images: %files copies files in from the host, %test holds a self-check run by apptainer test, %startscript runs when you start an instance, and %help feeds apptainer run-help.

Fakeroot: root inside, you outside

Installing packages in %post needs root inside the build. You don't have root on the cluster, and you shouldn't. --fakeroot uses a user namespace to map your user to root inside the container only:

apptainer build --fakeroot hello.sif exercises/01_hello.def
apptainer run hello.sif                 # Hello from Apptainer!

Iterate in a sandbox, freeze into a SIF

Rebuilding from scratch for every small change is slow. A sandbox is a writable directory-based container: build it once, shell in, install and test, then freeze it.

apptainer build --sandbox sandbox/ docker://ubuntu:22.04
apptainer shell --fakeroot --writable sandbox/   # apt install, edit, test …
apptainer build final.sif sandbox/

Test, inspect, sign

Three habits turn an image into something you can trust and hand to a colleague:

apptainer test conda.sif              # runs the %test block
apptainer inspect --deffile conda.sif # recover the embedded recipe
apptainer key newpair                 # once
apptainer sign conda.sif
apptainer verify conda.sif            # warns if the file changed since signing

Signatures live inside the SIF itself, so no keyserver is needed. On shared storage, where anyone with write access could replace a file, verification is cheap insurance.

Coming from Docker

Dockerfile keywords map almost one-to-one: FROM → Bootstrap/From, RUN → %post, ENV → %environment, COPY → %files, ENTRYPOINT → %runscript. Often you don't need to translate at all: build the Docker image as usual, push it to a registry, and point From: at it.

5Running under Slurm

The division of labour is simple: Slurm handles resources, Apptainer handles the environment. Slurm allocates nodes, CPUs, memory and GPUs. Inside that allocation, apptainer exec starts your software stack as you, with your normal file permissions. There is no daemon to coordinate with, so it runs fine under the scheduler's user context.

job.slurmExercise 5
#!/bin/bash
#SBATCH --job-name=container-job
#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=4
#SBATCH --time=00:30:00
#SBATCH --output=job_%j.log

module load apptainer          # if your site provides it as a module
apptainer exec --bind $SCRATCH/data:/data mytool.sif \
    python3 /data/analysis.py

On a single node, the script body runs once on the allocated node. For several tasks or nodes, prefix the command with srun, which starts one container per task across the allocation.

Rules of thumb
  • Bind the filesystem your data actually lives on. Don't assume it is mounted.
  • Match --cpus-per-task to the threads your program starts inside the container.
  • Pull once, not per node. If 64 nodes each pull from Docker Hub at job start, you create your own network bottleneck and may hit registry rate limits.

6GPUs and NVIDIA NGC

A GPU container needs two halves that live in different places. The CUDA toolkit and libraries (cuDNN, NCCL, PyTorch) ship inside the image. The driver belongs to the host, because it must match the host kernel. The --nv flag bridges the two: it binds the host's driver libraries and /dev/nvidia* devices into the container at run time.

Getting CUDA, cuDNN and NCCL versions to agree by hand is a common way to lose a week. NVIDIA's NGC catalog publishes GPU-optimised, tested images for PyTorch, TensorFlow and HPC applications such as GROMACS and NAMD. Most of the AI and CUDA base images can be pulled without an account; if a pull returns unauthorized, that image needs an NGC API key.

shellExercise 6
apptainer pull docker://nvcr.io/nvidia/pytorch:24.01-py3
apptainer exec --nv pytorch_24.01-py3.sif \
    python3 -c "import torch; print(torch.cuda.is_available())"   # True

In Exercise 7, participants built exercises/04_ml_gpu.def on top of such a base, adding scikit-learn and a %test block that checks the imports.

7MPI and I/O-heavy workflows

MPI: the hybrid model

The most common way to run containerised MPI codes is the hybrid model. The launcher (srun or mpirun) runs on the host, outside any container, and starts one apptainer exec per rank. Each rank runs its own container instance, and the MPI library inside the image talks to the host's MPI and interconnect stack.

srun apptainer exec mpi_app.sif ./my_mpi_program

The alternative is the bind model: the host's MPI installation is bind-mounted into the container at run time, so the image carries no MPI of its own. Some sites do this by default for full interconnect speed. It usually works, but ABI mismatches are confusing to debug. The Charliecloud best-practices guide covers both approaches in depth.

I/O

  • Avoid millions of small-file operations on the parallel filesystem. Pack datasets into larger files, or stage them to node-local NVMe or /tmp at job start.
  • Large read-only reference data (genomes, model weights) can be shipped as a SquashFS overlay instead of millions of files.
  • --overlay adds a writable layer on top of an image without rebuilding it.

8Capstone: an LLM fine-tuning job

The last exercise put everything together: an NGC base image, a definition file, GPU access, bind paths and Slurm. The recipe starts from NVIDIA's PyTorch image and adds the Hugging Face fine-tuning libraries:

exercises/05_llm.defExercise 8
Bootstrap: docker
From: nvcr.io/nvidia/pytorch:23.08-py3   # CUDA, cuDNN, PyTorch from NGC

%post
    apt-get update && apt-get install -y git
    pip install transformers datasets accelerate peft   # pin these, see section 9

%test
    python -c "import transformers; print(transformers.__version__)"

The Hugging Face cache

Models download to ~/.cache/huggingface by default, and on a 5 GB home quota a single 7B model fails the job. The fix is the same pattern as any other bind path: put the cache on scratch.

mkdir -p $SCRATCH/hf_cache
apptainer exec --nv \
    --env HF_HOME=/hf_cache \
    --bind $SCRATCH/hf_cache:/hf_cache \
    llm.sif python exercises/llm_training_script.py

Compute nodes are offline

This was the surprise during preparation. On JURECA, as on many supercomputers, compute nodes have no internet access. A job that calls from_pretrained("…") doesn't fail fast; it hangs while trying to reach the Hub until the job times out.

# on the login node, once
bash exercises/prefecth_model.sh

# in exercises/job_gpu_llm.slurm
export HF_HUB_OFFLINE=1
export TRANSFORMERS_OFFLINE=1
srun apptainer exec --nv --env HF_HOME=/hf_cache \
     --bind $SCRATCH/hf_cache:/hf_cache llm.sif python run_llm.py

With the cache prefetched and offline mode set, the GPU inference job finished in 9.1 seconds. Its CPU counterpart, exercises/job_cpu_matmul.slurm, reached about 566 GFLOP/s on a single node from inside the container.

9What broke on the cluster

Every exercise worked on my workstation the first time. On JURECA, several did not. The failures fell into a few families, and they are more instructive than the happy path.

Fakeroot without a subuid mapping

Full --fakeroot needs an entry for your user in /etc/subuid and /etc/subgid, set up by the admins. Without it, Apptainer falls back to a more limited mode. Simple builds still work, but package managers that change file ownership during installation can fail with errors that look unrelated to fakeroot. The fix was to keep %post steps simple, prefer pip and conda installs that don't change file ownership, and ask whether the site supports remote or admin-provided builds for heavier images.

Unpinned dependencies drift

A definition file that says pip install transformers produces a different image every month. Between my first test and the dress rehearsal, unpinned packages resolved to newer releases that expected a newer glibc and CUDA than the base image provided. The image still built and failed only at run time. Pin everything in %post, and pin the base image tag too. :latest means "whatever was published last".

Offline compute nodes

Covered above: any library that downloads on first use (Hugging Face, torchvision weights, NLTK data) will hang on a compute node. Prefetch on the login node and set the offline flags.

Quota and temp space

The first pull of a PyTorch image filled the 5 GB home quota through the layer cache, and builds failed when the temp directory didn't exist. Setting APPTAINER_CACHEDIR and APPTAINER_TMPDIR before the first command, as in section 3, solved both.

Checklist
  • Cache and temp directories on project or scratch storage.
  • Base image tag and every package version pinned.
  • A %test block that fails loudly.
  • Models and datasets prefetched before the job, offline flags set.
  • Data bound in, never baked in.

10Epilogue

We started with a single process on a shared kernel, packed a software stack into one SIF file, built our own images without root, and ran them under Slurm on CPUs, GPUs and across MPI ranks. The capstone combined all of it into an LLM job on a supercomputer whose compute nodes can't reach the internet.

Containers don't remove every portability problem. The CPU architecture, the host driver and the host MPI still matter, and an unpinned recipe isn't reproducible no matter how it is packaged. Within those limits, they move most of the "works on my machine" problem out of your way.

I skipped GUI sessions, instances for long-running services and the OCI-native runtimes in detail. Those will get their own posts.
